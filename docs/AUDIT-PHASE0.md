## T1 依赖安全体检

体检日期：2026-10-24
工具：`cargo-audit 0.22.2`、`cargo-deny 0.20.2`（均为 GitHub 预编译二进制，装在 `~/.cargo/bin`）
漏洞库：RustSec advisory-db 快照，1332 条（`~/.cargo/advisory-db`，浅克隆）
依赖规模：`Cargo.lock` 共 126 个 crate

## 结论一句话

**扫出 1 个真实漏洞 + 1 个被撤回版本 + 1 处许可证白名单缺口**，全部是传递依赖的补丁级升级，
我们自己的 `Cargo.toml` 一行都不用改。修完 `cargo deny check` 才能全绿。

## 发现 1：ctutils 0.4.3 —— RUSTSEC-2026-0385（有漏洞，必须修）

| 项 | 内容 |
|---|---|
| 漏洞 | `ctutils::Choice` 的掩码生成函数在 v0.4.4 之前可能生成**带分支**的代码；`u128` 比较在 32 位目标上也会分支。分支依赖秘密值 → 可能通过侧信道泄漏密钥 |
| 严重度 | RustSec 归为密码学实现缺陷（非常新，2026-10-23 发布） |
| 修复 | `ctutils >= 0.4.4`（当前最新 0.4.5） |
| 怎么进来的 | `zip 9.0.4` / `rars 0.11.0` / `sevenz-rust2 0.24.0` → `digest 0.11.3` / `sha1` / `sha2` / `hmac` / `pbkdf2` → `ctutils 0.4.3` |
| 用户会怎样撞上 | 本地解压工具，攻击者通常不在对面，**现实风险低**；但走的是「密码校验、哈希比对」这条加密路径，属于该修就修的一类，而且 `deny.toml` 里 vulnerability 默认 deny，门禁会一直红 |

修法：`cargo update -p ctutils --precise 0.4.5`（只动 `Cargo.lock`）

## 发现 2：inout 0.2.3 —— 被撤回（yanked）

| 项 | 内容 |
|---|---|
| 情况 | 该版本已被 crates.io 撤回（yanked），最新 0.2.5 |
| 怎么进来的 | `aes 0.9.3` / `cbc 0.2.1` → `cipher 0.5.2` → `inout` |
| 影响 | yanked ≠ 有漏洞，但意味着上游不建议再用该版本；`cargo-deny` 门禁会报 |

修法：`cargo update -p inout --precise 0.2.5`

## 发现 3：许可证白名单缺口（libbz2-rs-sys）

`libbz2-rs-sys 0.2.5`（`bzip2 0.6.1` → `sevenz-rust2`）的许可证是 `bzip2-1.0.6`，
不在 `deny.toml` 的 allow 列表里 → `licenses FAILED`。

- `bzip2-1.0.6` 是宽松自由许可证，与 MIT 兼容，可放行
- 顺带两条白名单从来没被用到（`BSD-2-Clause`、`ISC`），留着会一直报警告

修法：allow 列表加 `"bzip2-1.0.6"`，删掉没用到的两条（或留注释说明未来可能用到）

## 顺带发现：deny.toml 与新工具不兼容（**已改**）

cargo-deny 0.20 的配置 schema 变了，老配置直接跑不起来：

| 旧写法 | 新版 | 处理 |
|---|---|---|
| `vulnerability = "deny"` | 键已移除（默认就是 deny） | 删掉 + 注释说明 |
| `yanked = "deny"` | 键已移除（默认 deny） | 删掉 + 注释说明 |
| `unmaintained = "warn"` | 只接受 `all` / `workspace` / `transitive` / `none` | 改 `workspace`（只报工作区直接依赖，避免传递依赖噪音） |

## 验收标准（修完要看到）

1. `cargo audit --no-fetch` → `0 vulnerabilities found`，无 yanked
2. `cargo deny check` → advisories ok / bans ok / licenses ok / sources ok
3. `bash tests/all.sh` 仍 15 通过 / 0 失败（证明升级没改坏行为）
4. 补丁升级只动 `Cargo.lock`，`Cargo.toml` 不变

## T7 多语言完整度体检

体检日期：2026-10-24
方法：拿 `locales/zh-CN.toml` 当基准，用 Python `tomllib` 递归展平成 `a.b.c` 形式的 key 逐语言比对；
再对 `gui/lib/` 全部 14 个 Dart 文件扫硬编码中文。

### 引擎 / CLI 侧：**完整，无缺口**

7 个语言包全部 **121 个 key，零缺失、零空值、零多余 key**：

    语言            key数  缺key  空值  多余key
    en-US.toml      121     0     0      0
    es-ES.toml      121     0     0      0
    ja-JP.toml      121     0     0      0
    ko-KR.toml      121     0     0      0
    ru-RU.toml      121     0     0      0
    zh-TW.toml      121     0     0      0

「各语言里与中文一字不差」的那几条，逐条看过，**全是纯格式串**（`'   {lock} {size}   {path}'`、
`'   ⚠ {warn}'` 等），没有文字可翻，不算漏译。仅 `ja-JP` 有两条真文字与中文相同：
`tier.common = '常用版'`、`tier.full = '全能版'`（日文汉字写法与中文一致，可接受）。

加载链路也核实过：`build.rs` 扫描 `locales/*.toml` 编译期嵌入 + 支持外部覆盖
（`$YSHTY_LOCALES/` → `~/.config/yshjy/locales/` → 当前目录 `locales/`），`src/i18n.rs` 有兜底断言。

### 界面（Flutter GUI）侧：**不是缺翻译，是根本没接**

| 证据 | 数字 |
|---|---|
| `gui/lib/` 里引用 i18n / AppLocalizations / Intl.message 的文件 | **0 个** |
| 硬编码中文的 Dart 文件 | **11 / 14 个** |
| 硬编码中文字符串出现次数 | **401 处** |

原因不是偷懒，是架构决定：D21/N1 定的是「**引擎只给码、壳自己查文案**」，所以错误码/诊断码
的人话全在 `gui/lib/humanize.dart`（87 行）+ 各页面里；引擎的 7 语言语言包只服务 CLI 与引擎自身消息。

项目自己也如实写着（`settings_page.dart:341`）：
「界面文案多语言切换（引擎已支持 7 种语言，界面文案还没抽成语言包）」。

**要做界面多语言，工作量不是补翻译，而是**：把 `humanize.dart` 三张表 + 401 处中文抽成
Dart 侧语言包（ARB 或自建 `Map<String, String>` 按语言加载），涉及 11 个文件。

### 发现一处会误导人的文案（小，但真人会撞）

`settings_page.dart:327` 把「界面语言」列在「其它（改 config.toml）」区块里，并写出 7 种语言码：

    _kv('界面语言', 'zh-CN / zh-TW / en-US / ja-JP / ko-KR / ru-RU / es-ES')

而 `config.toml` 的 `general.language` 只影响**引擎/CLI 文案**，改它界面一个字都不会变
（界面 0 处读语言包）。用户照这行去改配置，会以为界面能切语言，结果没反应 —— 属于「文案比实现承诺得多」。
建议改成明说「界面语言：中文（界面多语言尚未实现，见下方待办）」，或在设置页做一个真能切的开关。

## T9 数据安全复核

体检日期：2026-10-24
问题：**「这工具会不会弄坏我原有的文件」**。
方法：在 scratch 里造四个真实场景，逐个跑 `target/release/yshjy` 并核对落地文件、退出码、临时文件。
样本用仓库自带的 `tests/data/`（`C1_plain.zip` / `D1_truncated.zip` / `D4_corrupt_member.zip`）。

### 好消息：三条「不弄坏用户文件」的核心行为实测通过

| 场景 | 实测结果 |
|---|---|
| 同名冲突（默认策略 rename） | 两次解压到同一目录，我预先写入的 `文件1.txt` 内容**一字未改**，新文件落成 `文件1 (1).txt` ✓ |
| 截断的包（`D1_truncated.zip`） | 直接拒绝，输出目录**0 个文件**、0 个临时文件 ✓ |
| 包内单个成员损坏（`D4_corrupt_member.zip`） | 解开 4/5，坏的那条（`payload/random.bin`，Invalid checksum）**不留空壳**，文案清楚 ✓ |
| 输出目录没写权限（chmod 555） | 不落地任何文件 ✓（但文案错了，见问题 P3） |

### 问题 P1（最重）：写到一半被中断 → 半截文件顶着最终文件名留在磁盘上

    ulimit -f 40  # 限制单文件 20 KB，模拟「写到一半没空间」
    yshjy -o p4 tests/data/C1_plain.zip
    → 退出码 153（128+25，进程被 SIGXFSZ 杀掉）

    落地清单：
         0  p4/payload/empty.txt
     40960  p4/payload/random.bin      ← 包内应为 204800 字节
    （剩下 3 个文件根本没解，包括 中文目录/文件1.txt、说明.txt）

用户会怎样撞上：解一个 8 GB 的大包，中途磁盘满 / 拔盘 / 崩溃 / 被 kill，目录里躺着一个
名字正常、大小减半的文件，**没有任何 `.tmp` 后缀、没有任何失败标记、程序也没留下一句话**
（进程是被信号杀的，来不及说话）。之后他拿着这个文件去用，坏了也想不到是解压没完成。

对比：正常解压同一包，`random.bin` 是完整 204800 字节。

**诚实标注局限**：真实磁盘满返回的是 `ENOSPC` 错误（引擎有机会优雅报错），我用 `ulimit -f` 触发的是
`SIGXFSZ`（内核直接杀进程），比 ENOSPC 更极端。真实 ENOSPC 需要小容量 tmpfs 才能测（要 sudo），
还没测 —— 归到 T8 异常场景那项。

### 问题 P2：「重名策略」是假开关（配置与界面都不生效）

实测三种策略，结果**完全一样**：

    策略       落地产物                        原文件内容
    rename     文件1.txt + 文件1 (1).txt       未改动
    replace    文件1.txt + 文件1 (1).txt       未改动   ← 本该覆盖
    skip       文件1.txt + 文件1 (1).txt       未改动   ← 本该跳过

代码侧确认（`grep` 全仓）：

- `src/extract.rs:31` `enum Overwrite { Skip, Replace, Rename }`，`#[default] Rename`
- `overwrite` 字段只在 `src/unpack.rs:236/246/256/265` 内部自传递，**没有任何一处从 config 或协议读值赋给它**
- `src/config.rs` 解析了 `output.conflict`，但全仓只有 `src/report.rs:499` 打印它（诊断用）
- `gui/lib/pages/settings_page.dart:238` 有「重名策略」下拉，保存进 config → 引擎不读

即：**引擎永远用 Rename**。用户把 config 改成 `conflict = "replace"`、或者在设置页选「覆盖」，
解压行为一点不变。这是技能里明令禁止的「假开关」。

好消息是默认值选了最安全的 Rename，所以没造成数据损失；坏消息是给了用户一个不存在的控制权。

### 问题 P3：权限不够被报成「数据损坏」

    chmod 555 out && yshjy -o out tests/data/C1_plain.zip
    ❌ C1_plain.zip —— 中间有一段数据丢了（0 B，用时 0.0 秒）   ← 退出码 1
       ℹ 这个文件看起来是：ZIP 压缩包（401 KB）

真实原因是「目录不让写」，包本身完好。用户看到「数据丢了」会去重新下载这个 401 KB 的包，
白折腾一轮还不知道真正要改的是目录权限。这正是「把工具的限制说成用户的文件坏了」，
应该给独立原因（无写权限 / 目标目录不可写）。

### 问题 P4：自动抓密码的启发式读过界了

场景 2/3/4 每次都会先打印：

    ℹ 解压码是从旁边的说明里找到的：.../yshjy/tests/README.md: | `C8_zipcrypto.zip` | 410,924 | `zip -e -P zipcrypto123` | ...

它把**包的父目录里的 `README.md`** 当成「说明文件」，把整行 Markdown 表格（含「密码」字样）
当成候选密码。即使这个包（`C1_plain.zip`）根本不需要密码，也要先试一遍这串垃圾。

风险：① 无用密码尝试拖慢/触发错密码计数的误判；② 把无关文档当密码源，行为不可预期。
合理范围应限定为「包同名说明文件（`xxx.说明.txt`）」+ 用户密码本，不要往上层目录乱翻。

### T9 小结

「会不会弄坏你原有的文件」→ **不会**（冲突改名、坏包不全落地、原内容零改动）。
「失败了会不会看起来像成功」→ **会**（P1：半截文件顶真名、无标记）。
加上 P2/P3/P4，四项都不是致命 bug，但 P1 与 P3 都会让用户做出错误判断。

## T8 异常场景（部分完成）

体检日期：2026-10-24
已测：输出路径异常 5 种、解压中途强杀、重试自愈性。
**未测（需要 sudo 挂载）**：真实磁盘满（`ENOSPC`）、解到一半拔盘 —— 见文末待办。

### 通过的项目

| 场景 | 表现 | 判定 |
|---|---|---|
| `-o` 指向深层不存在的目录 | 自动建好 `a/b/c`，5 个文件正常落地，退出码 0 | ✓ 好 |
| `-o` 指向已存在的普通文件 | 拒绝，退出码 1，**那个文件内容一字未动** | ✓ 安全（文案差，见下） |
| 输出目录是符号链接 | 跟随链接写到真实目录，5 个文件 | ✓ 合理 |
| 恶意包 `../escaped.txt` 路径穿越 | 只跳过那一条，理由明确（`路径不安全被拒: parent_dir_in_path`），其余 1 条正常解，退出码 5，**上级目录没有出现逃逸文件** | ✓✓ 安全策略正确 |

路径穿越这条是本项最要紧的安全行为，实测守住了，而且给的是独立原因、没折成「数据损坏」。

### 问题 P5：两种常见的用户错误都被报成「内部错误」

    -o 指向一个普通文件   → ❌ 内部错误（退出码 1）
    -o 路径超长(300+ 字符) → ❌ 内部错误（退出码 1）

「内部错误」等于告诉用户「这不是你的问题也不用管」，但这两条**都是用户能自己改的**：
前者是选错了目标（选到文件上了），后者是路径太长（换个短目录名就好）。
应该分别给「目标路径不是文件夹」「路径太长，换个短一点的名字」。

### 问题 P6：解压中途被强杀 → 半截文件 + 「重试不能自愈，反而制造重复」

实测（1 GB 包，`timeout -s KILL 0.4` 强杀，模拟断电 / 崩溃 / 用户强制关闭）：

    被杀后落地（退出码 137）：
      104857600  big/part0.bin     ← 完整
       49098752  big/part1.bin     ← 只写了 47%，名字完全正常
       临时文件（.tmp/.part）：0 个

用户看到这个目录，**没有任何东西提示 part1.bin 是坏的**。

然后他做最自然的动作——重新解压一次：

    重试退出码 0（看起来成功了）
    文件数：2 → 12，其中：
      104857600  big/part0.bin        ← 上一轮的
      104857600  big/part0 (1).bin    ← 这轮又写了一份完整的
       49098752  big/part1.bin        ← 【上一轮的半截文件，仍在】
      104857600  big/part1 (1).bin    ← 这轮的完整版
      …part2 ~ part9 全部完整

结果：① 那个叫 `part1.bin` 的**坏文件永远不会被修好**（改名策略避开它）；
② 目录里同名文件成对堆积（100 MB 的重复垃圾）；
③ 磁盘占用 1 GB → 约 1.15 GB；④ 用户拿哪个都对不上，得靠大小自己猜。

这条与 T9 的 P1 同根：**缺「先写临时名、写完再原子改名」**。修法也是同一个：
写 `<名字>.yshjy-part`（或同目录 `.tmp`），成功后 `rename` 成正式名，失败落盘时清理。
一旦有这一步，重试就能覆盖半截文件、自愈。

### 未测项（要 sudo，等你点头）

| 场景 | 为什么必须 sudo | 怎么测 |
|---|---|---|
| 真实磁盘满（`ENOSPC`） | 需要挂一个小容量 tmpfs（如 `mount -t tmpfs -o size=64M`） | 解 1 GB 包解到该 tmpfs，看是否优雅报错、有没有残留 |
| 解到一半拔盘 | 需要 loop 设备模拟可移除盘 | 解压大包时 `umount -l` / 拔 USB，看进程报错与残留 |
| 断电 | 真断电测不了，用 SIGKILL 近似（已测，见 P6） | — |

## T2 测试覆盖体检

体检日期：2026-10-24
工具：`cargo-llvm-cov 0.9.1` + `llvm-tools-preview`（均新装，预编译二进制）
命令：`cargo llvm-cov --release --text --no-fail-fast`（带插桩重编译后跑全部单测）
原始明细：`cov.txt`（2.5 万行，跑完在 scratch，24 小时后自动清）

### 总览

    **项目总计：9687 / 14618 行 = 66.3%**（44 个源文件参与统计）

303 个单测分布在核心引擎上，整体 66% 对一个解压器来说不算差；但分布**很不均**。

### 最裸的模块（按覆盖率升序）

| 覆盖率 | 可执行行 | 文件 | 说明 |
|---|---|---|---|
| **0.0%** | 1356 | `src/main.rs` | CLI 入口，一行没进插桩测试（口径问题，见下） |
| **7.5%** | 280 | `src/report.rs` | 诊断包生成 |
| **8.1%** | 571 | `src/api.rs` | 协议命令实现层 |
| **26.2%** | 237 | `src/serve.rs` | **`--serve` 协议服务器**——界面全部交互的唯一通道 |
| 38.9% | 18 | `src/layout/mod.rs` | |
| 59.6% | 280 | `src/crash.rs` | 崩溃报告 |
| 59.7% | 216 | `src/repair.rs` | 修复 |

### 健康的部分（核心解压路径）

    extract.rs            86.8%    extract_rar.rs        60.8%
    extract_stream.rs     69.6%    extract7z.rs          72.3%
    unpack.rs             76.7%    batch.rs              93.2%
    select.rs             93.9%    safety.rs             87.4%
    io/*                  85~100%  pack/*                77~100%

也就是说：**「能不能把包解开、解得对不对」这块是有测试守着的**，缺口集中在「外圈」——
入口、协议、报告、修复。

### 两个必须说清的口径问题（否则会误判）

1. **`main.rs` 的 0% 不等于「CLI 没测」**。`tests/smoke.sh`（25 项）和 7 个协议探针都是
   跑**编译好的二进制**，`llvm-cov` 只统计被插桩的 lib 测试进程，外部脚本的覆盖不计入。
   CLI 的真实验证在 smoke.sh 里，只是这份报告看不见。
   想让 CLI 也进覆盖率，得把入口逻辑挪进 lib，用 `assert_cmd` 跑集成测试。
2. **`serve.rs` 26.2% / `api.rs` 8.1% 是真缺口**，不是口径问题：协议层几乎没有单元测试，
   而界面（Flutter）100% 依赖它。7 个协议探针只覆盖了 select / level / pack_cover / sfx /
   cancel / serve_eof 这几条，剩下的大部分命令没人测。
