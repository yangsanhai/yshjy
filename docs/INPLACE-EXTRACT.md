> 起因：用户看到有项目「边解压边删除压缩包」，问我们能不能加。
> 这跟「解压完再删源」是两件事：**峰值磁盘占用**从「包 + 解出」降到「解出」，8.7 GB 的包不再是 17 GB 的活。

## 1. 三个项目分别在干什么

| 项目 | 语言/平台 | 路线 | 一句话 |
|---|---|---|---|
| **xevrion/hatchzip** | Rust，跨平台 | **从尾部倒着解 + 逐批 truncate** | 工程最完整：journal 事务、断电可续、打洞处理单大文件、分卷当逻辑文件 |
| **auto-Dog/delete_when_unzip** | Python，Windows 为主 | **shift_then_truncate / 分卷删卷** | 直白实用：单 ZIP 用「搬移已读部分再截断」，分卷读完一卷删一卷；带 Tkinter GUI |
| **harlixay7/ReclaimArc** | Windows (NTFS/ReFS) | **文件系统特性原地回收** | 靠 NTFS/ReFS 的稀疏/压缩能力做事务性回收，跟 Linux 无关 |
| agouin/peel（旧参考） | Rust | 边下载边解压 + frame 级断点 | 管的是「下载」，不是「解压删源」，但断点思路同源 |

## 2. 核心技术矛盾：文件只能从尾部变短

- **所有系统/文件系统**都支持 `ftruncate` / `SetEndOfFile` —— 但只能砍**尾部**。
- 想释放文件**开头或中间**的字节，需要「打洞」：
  - Linux `fallocate(FALLOC_FL_PUNCH_HOLE)`
  - Windows `FSCTL_SET_ZERO_DATA`
  - macOS（APFS）`F_PUNCHHOLE`
  - **FAT32 / exFAT 不支持**，各系统行为还不一样。

而压缩包是**顺序读**的：读指针从前往后走，被吃掉的是**前部**，正好是不能 truncate 的那头。

于是业界分成两条路：

### 路线 A：倒着解（hatchzip 选择）

把归档看成「一串能独立解码的单元」（ZIP 一个条目、7z 一个 solid 块、tar 一个条目），
**从最后一个单元开始解**，每解完一批就 `truncate(committed_len)` 把尾巴砍掉。

关键难点它都解决了：
1. **ZIP / 7z 的索引在文件尾部**，砍尾巴会先砍掉索引 → 所以在动刀之前，先把
   「最后一个单元之后的全部字节」复制到 `<archive>.hatchzip-tail` 并记 CRC；
   之后解析走一层虚拟 Reader：尾部以下读真实文件（已被砍的区域读 0），尾部以上读保存的 tail。
   ZIP 库反向扫 EOCD 时空区永远匹配不上签名，所以行为正确。
2. **事务顺序固定**：解一批 → `syncfs`/fsync → 写 journal（`committed_len`）→ 才 truncate。
   断电最多丢一批的重解，绝不出现「源没了、输出也没有」。
3. **solid 块只能整块解**（7z 默认把整个包塞进一个 solid 块）→ 那就整块解完才释放，
   它会在开跑前就把「最大单元」算进空间检查里，直接告诉用户省不了多少。
4. **单个巨大文件**（30 GB 一个条目）没法「解完再砍」→ 改用**打洞 + 流式断点**（每 256 MiB 一个可重启点）。
5. **分卷**：虚拟合并成一条逻辑流，truncate 到某长度 = 删掉完全落在后面的卷、缩短跨边界那个卷。

### 路线 B：打洞释放已读区间（简单但 Linux 限定）

顺序读、顺序解，把「已安全落盘的源偏移之前」这段用 punch hole 释放掉。
文件逻辑大小不变、占用块被回收，`ls` 看着还是 8.7 GB，但 `du` 已经掉下来了。

### 路线 C：分卷读完就删卷（delete_when_unzip 的做法之一）

分卷包最容易：`.001` 解完、确认落盘 → 直接 `rm` 掉 `.001`。峰值少一份卷的空间。
不需要打洞、不需要倒着解，风险最低。

## 3. 放到 yshjy 身上，哪些能用

先看我们的约束：
- 引擎 `#![forbid(unsafe_code)]` —— 打洞不能自己写 `unsafe libc`；但可以用 `rustix`（安全封装）或
  把打洞做成一个受控的 `unsafe` 小模块（外壳 `src/main.rs` 没禁 unsafe）。
- 解码全靠库（`zip` / `sevenz-rust2` / `rars` / `tar`），都是顺序流式 API，**没有「跳到第 N 个条目」的入口**。
- 我们已经有：条目级断点续传（JSONL）、原子写入（`PartFile`，先写 `.yshjy-part` 再改名）、分卷归组。
- 我们的主场景是**伪装包**（`x.mp4` 里藏 ZIP/7z），数据在中间偏后，前面是外壳视频。

| 方案 | 对我们可行性 | 收益 | 风险/成本 |
|---|---|---|---|
| **C. 分卷读完删卷** | ✅ 高 —— 我们分卷归组、卷名推导都现成 | 分卷场景峰值省 (N-1)/N | 低。失败要能从剩下卷续（已有续传） |
| **B. 打洞（punch hole）** | 🟡 中 —— 需要 `rustix`，且**必须每批 fsync 后才打洞** | 单文件大包峰值几乎减半 | 中。fsync 会降速；断电前落盘必须保证；FAT/exFAT 要退回 |
| **A. 倒着解（hatchzip 全套）** | ❌ 低 —— 要重写解压驱动层（逆序遍历 + 虚拟 Reader + tail 转存 + journal v3） | 全格式通用 | 高。`zip`/`sevenz-rust2` 都没有「逆序读」入口，等于自己写一层 |

## 4. 建议的落地顺序（每档独立可用，不互相阻塞）

### 第一档：`--reclaim`（分卷删卷）—— 建议先做

- 触发：`yshjy --reclaim 包.z01`（或 `--reclaim` 配合 `--delete-source`）
- 行为：解完一卷、该卷所有条目都已 `fsync` 落盘 → 删这一卷；日志记一条「第 k 卷已消费」。
- 拒绝条件：卷里还有没解出的条目 / 用户取消 / 有任何 IO 错误 → 立刻停手，剩下的卷一个不删。
- 验收：3 卷共 3 GB 的包，峰值占用 ≤ 2 GB；中途 `kill -9` 后能续；续完卷删干净、内容逐字节对得上。

### 第二档：`--reclaim` 里加打洞（Linux，顺序解压路径）

- 每解完一批（比如 256 MB）→ `fsync` 输出 → 记 journal → 对
  `[数据起点, 已消费位置)` 打洞释放。**顺序不能反**：先落盘再打洞，否则断电 = 双丢。
- 文件系统不支持（FAT/exFAT/网络盘）→ 自动退回「解完再删」，并在结果里说明为什么没省空间。
- 验收：8.7 GB 伪装包解到 50% 时 `du` 已降到 ≈4 GB，`ls` 大小不变；断电模拟（`kill -9`）后重跑能续；
  产物 sha256 与常规解压逐字节一致。

### 第三档：真·倒着解（只有前两档不够再上）

要动 `unpack.rs` 的驱动层，工程量大，且 7z 的 solid 块天生省不了。
**除非**用户的实际包都是 ZIP 且都是单文件超大条目，否则不建议现在做。

## 5. 安全铁律（无论做哪档，这几条不能破）

1. **默认关闭**：不加参数时行为与现在完全一致，绝不悄悄删源。
2. **先落盘、后释放**：`fsync` 输出文件 → 记 journal → 才 truncate / punch / 删卷。顺序反了就是「数据双丢」。
3. **只在完全成功时删整包**：有失败条目 / 跳过 / 取消 → 一个字节都不删，结果里说明原因。
4. **打洞不可逆**：只对「已确认落盘」的区间打洞；journal 里记 `committed_len`，重跑时据此判断还能不能续。
5. **说清楚不可恢复**：CLI 在删之前把要删的文件和将释放的空间打出来；界面红字提示，完成页报「已释放 X GB」。
6. **分卷整组处理**：卷名要么全删要么全留，绝不半套。
7. **不动别人的东西**：只处理本次解压的源包本身；`.sha256` / `.说明.txt` / 密码本 / 内层包一律不动。
