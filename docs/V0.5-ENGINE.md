# v0.5 引擎侧设计（事件 / 进度 / 挑选 / 批量）

> 日期：2026-10-17　范围：**只做引擎与 CLI**，GUI 与跨平台构建留 v0.6
> 目标：把「GUI 的地基」修好 —— 界面 S3（预览挑选）、S6（处理中进度）、S13（批量队列）都靠这一层

---

## 一、为什么要先做这一层

`v0.4.0` 的引擎是「一次调用、一个文件、结束时才返回」的形状：

```
调用 extract() ──────────────── 8 分钟 ────────────────→ 返回 Report
                  ↑ 这期间外壳什么都看不到
```

GUI 需要的是**看得见的中间过程** + **能中途反悔**：

| 界面状态 | 引擎必须提供 |
|---|---|
| S3 列出内容、勾选、再解压 | 预览结果（结构化）+ 生效的挑选（selection） |
| S6 进度条 + 剩余时间 + 当前文件 | 事件流（进度事件）+ 取消 |
| S13 批量队列（8 个文件排队） | 批量任务模型 + 每个任务的独立结果 |
| S8 部分成功（救出 340/351） | 三层结果（条目级 vs 归档级分开） |
| S11 已取消 | 取消是**独立语义**，不是「失败」 |

## 二、事件模型（`src/event.rs`）

**原则**（照抄 7-Zip 的回调契约，但用类型系统表达，见 `refs/tech/7zip-工程层.md` §2.7）：

- 事件是**纯数据**，`serde` 可序列化（FFI 侧原样转 JSON → Dart `Stream`，见 BACKEND-SPEC §1.3）
- 事件**不含面向用户的中文文案**（只带码 + 参数，渲染归外壳）
- 进度事件与结果事件**分通道**：进度可高频、可合并；结果不丢

```rust
pub enum Event {
    // ── 任务级 ──
    JobStarted { job: u64, path: String, size: u64 },
    JobFinished { job: u64, outcome: Outcome },

    // ── 阶段级 ──
    StageStarted { job: u64, stage: Stage },        // Locate | List | Extract | Verify | Pack
    StageFinished { job: u64, stage: Stage, millis: u64 },

    // ── 扫描（双维度进度，见 §2.3 台账）──
    ScanProgress { job: u64, files: Option<(u64, u64)>, bytes: Option<(u64, u64)> },

    // ── 预览结果（S3 的数据源）──
    PreviewReady { job: u64, entries: Vec<EntryView>, hint: PreviewHint },

    // ── 解压进度（唯一的"当前在解哪个文件"来源）──
    ExtractProgress { job: u64, done_bytes: u64, total_bytes: u64,
                      done_files: u64, total_files: u64, current: Option<String> },

    // ── 条目级结果（S7/S8 的明细）──
    EntryFinished { job: u64, index: u64, path: String, result: ItemResult },

    // ── 需要用户决策（S4/S5/S10）──
    PasswordNeeded { job: u64, attempts: u32, candidates: u32 },
    SpaceShortage { job: u64, needed: u64, available: u64 },

    // ── 诊断与警告（归档级，不打断流程）──
    Diagnostic { job: u64, code: DiagnosticCode, flags: ArchiveFlags, note: String },
}
```

**事件出口**：引擎不返回 `Vec<Event>`（8GB 解压会产生几十万条），而是**推送 + 有界队列**（台账 `M1`）：

```rust
pub trait EventSink: Send + Sync {
    /// 送出一条事件。实现方必须非阻塞；队列满时**丢最旧的进度事件**（结果事件永不丢）
    fn emit(&self, ev: &Event);
}
```

配套：
- `NullSink` —— 什么都不做（测试/管道用）
- `ChannelSink` —— 内部有界 `VecDeque` + `Mutex`，供 CLI 主线程按需抽取
- **进度合并**（台账 `F2`）：同 `job` 的连续 `ExtractProgress` 在队列里只保留最后一条

## 三、进度与取消（`src/progress.rs`）

### 3.1 拆成两个对象（修掉 7-Zip 的过度加锁，台账 §6.4）

```rust
pub struct ProgressSnapshot { /* 全 AtomicU64，读不加锁 */ }
pub struct CancelToken { /* AtomicBool + 原因 */ }
```

**为什么不学 7-Zip 的 `CProgressSync`**：它把「进度数字」和「停止/暂停标志」塞进同一个 `CCriticalSection`，
每次读进度都要拿锁 —— 而进度全是单调累加的 `u64`，用 `AtomicU64::fetch_add` 免锁更合适（台账 §2.6）。

### 3.2 多任务聚合（台账 §2.6）

```rust
pub struct ProgressAggregator { /* 每任务槽位 + AtomicU64 总和 */ }
```

每个任务往自己的槽位 `fetch_add` 增量，聚合器把总增量转发给上层 —— 上层只见到**一条单调递增的进度流**，
不会因为任务切换而跳变/回退。

### 3.3 嵌套进度折算（台账 §3.5，**我们是刚需**）

一个伪装包经常是「ZIP 里套 7z」——内层解压的进度必须折算成外层段内的进度，
否则界面会看到进度条先跑一半再重新从 0 开始。

```rust
pub struct LocalProgress { /* offset + 段长度 + base，RAII guard */ }
```

**修掉 7-Zip 的缺陷**：它用 `Init/Clear` 手动配对（漏一个就错），我们用 RAII（`Drop` 时自动结束该段）。

### 3.4 剩余时间估算（台账 §6.7）

7-Zip 的平滑算法和 UI 代码混在一起（不可复用），我们写干净的 `EtaEstimator`：

- 指数滑动平均（`α = 0.3`）+ **速度窗口**，避免数字乱跳
- 前 1 秒不出估算（样本太少，估出来是错的，不如不显示 —— 呼应 UI-SPEC 原则 5）
- 只在「速度样本 ≥ 3 且已过 1 秒」才给 `Option<Duration>`

### 3.5 取消（台账 §5.8 / 审查 B1）

- `CancelToken::cancel()` → 读取层 `InterruptibleReader` 每 1 MiB 检查一次（`src/io/interrupt.rs` 已有）
- 取消**不是错误**：`Outcome::Cancelled` 独立成档，退出码 130（SIGINT 惯例）
- 取消后**已解出的文件保留**（用户可能就想要那些），在报告里标注「已取消，完成 N/M」

## 四、三层结果模型（`src/error.rs` 扩充，台账 §5.2）

现状只有「一次操作一个 `ErrorCode`」，**缺两层**：

```
层1  调用级   ErrorCode          这次调用成了吗？          ← 已有
层2  归档级   ArchiveFlags       这个包有什么毛病？        ← 新增（位图）
层3  条目级   ItemResult         第 47 个文件对不对？      ← 新增
```

```rust
pub struct ArchiveFlags: u16 {   // 抄 7-Zip PropID.h:123-134 的 11 位，去掉字符串通道
    IS_NOT_ARC | HEADERS_ERROR | ENCRYPTED_HEADERS | UNAVAILABLE_START | UNCONFIRMED_START
    | UNEXPECTED_END | DATA_AFTER_END | UNSUPPORTED_METHOD | UNSUPPORTED_FEATURE
    | DATA_ERROR | CRC_ERROR
}

pub enum ItemResult { Ok, Skipped, CrcError, DataError, Encrypted, NotExtracted }
```

**退出码集中**（台账 §7.6，7-Zip 的反面案例）：`Outcome::exit_code()` 放在引擎里，CLI/GUI 都调它，
绝不各壳自己算。

```rust
pub enum Outcome { Success, Partial, Cancelled, Failed(ErrorCode) }
```

`Partial`（如救出 340/351）—— 台账 §5.1 指出我们**缺这一档**，CLI 现有退出码 5 就是给它预留的。

## 五、预览挑选（`src/select.rs`）

界面的 S3 是「列出 → 勾选 → 开始解压」，所以引擎必须能：
① 不用写完盘就能列出内容；② 按用户的勾选只解一部分。

```rust
pub struct Selection {
    mode: SelectMode,          // All | Only(索引集) | Matching(模式) | Required(只解必需)
    include: Vec<u64>,         // 条目索引
    pattern: Option<String>,   // 通配（`*.exe`、`游戏数据/*`）
    skip_dirs: bool,
}

pub struct PreviewEntry {      // 条目视图（不含内容，只有元数据）
    index: u64, path: String, size: u64, encrypted: bool,
    is_dir: bool, modified: Option<i64>, is_risky: bool,   // is_risky = 可执行/脚本（安全提示）
}

pub struct Preview { entries: Vec<PreviewEntry>, total_size: u64, encrypted_count: u64, hint: PreviewHint }
```

`PreviewHint`：给外壳的**不含文案**的提示码（`VolumesMerged` / `NestedArchive` / `NeedsPassword` /
`LooksTruncated` / `MiddleOfFile`），渲染成 UI-SPEC 里那几句「ℹ️ 检测到 2 个分卷，会自动合并」。

**条目索引稳定**：`index` 就是归档内的序号，从预览到解压**全程不变**（GUI 勾选的锚点）。

## 六、批量队列（`src/batch.rs`）

```rust
pub struct Job { id: u64, input: PathBuf, dest: PathBuf, state: JobState }
pub enum JobState { Queued, Running(Stage), Done(Outcome), Skipped(String) }

pub struct BatchOptions {
    jobs: usize,              // 并行度（默认 1 = 磁盘友好，见配置 §2.2）
    continue_on_error: bool,  // 默认 true（一个坏了不影响其余）
    password: Option<String>,
    selection: Selection,
    policy: OutputPolicy,     // 输出目录策略（智能解压三规则，UI-SPEC §9.2）
}

pub struct BatchReport { jobs: Vec<JobOutcome>, ... }   // 含 exit_code() / summary 计数
```

要点：
- **输入展开**：给一个目录 → 递归找可疑文件（`.mp4/.mkv/.zip/.7z/.rar/分卷首卷`），按体积倒序
- **失败隔离**：单个任务失败只记进报告，不打断队列（隐写者的 bug：批量成功率恒 100%，见 `00-总览` §3）
- **并行**：默认 1（顺序）。>1 时用 `std::thread` 手动分片，**必须有退回串行路径**（台账 §2.5：并行路径必须有 fallback）
- **输出目录策略**（智能解压三规则）：单条目 → 直接解到当前目录；多条目 → 建同名文件夹；重名 → 追加 `(2)`
