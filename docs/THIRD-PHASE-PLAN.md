## A. 预览树 + 部分解压（界面）

### 依据

- `refs/analysis/07-竞品界面调研.md:616-631`（PeaZip）：**面包屑地址栏** + **左侧「smart treeview」就是包内目录树**；
  状态栏常驻 `3 dir(s), 6 file(s), 1.1 GB`；可开关的列里**默认展示「压缩后大小」**（一眼看出哪个压不动）。
- 同文件 `:625-627`：PeaZip 官方明确「**出于安全，未明确请求前不解压任何内容**」——
  这条直接支持我们「树只读清单、不为了预览去解压」的做法（我们本来也只读头，等于天然合规）。
- `docs/REFERENCE-INDEX.md`「预览树 + 部分解压」行：落点写的就是「预览页平铺 → 树形结构 + 勾选 + 面包屑」。

### 现状

- 预览是**平铺列表**：`gui/lib/pages/home_page.dart:1511`（`ListView.builder`，`itemCount = pv.entries.length`）。
- 勾选状态存在 `_picked`（存的是 `EntryItem.index`），全选/全清在 `:1483-1489`。
- **引擎侧不需要改**：`src/select.rs:8` 明写「条目序号 `index` 从预览到解压全程不变，这就是 GUI 勾选的锚点」，
  且 `Selection` 支持「指定序号 / 通配 / `required`」三种（`src/select.rs:20,22,50,58`）。

### 设计决策

1. **树由前端纯函数构建**（不放引擎）：输入 `List<EntryItem>`，按 `path` 的 `/` 分层聚合成节点树。
   节点字段：`name / 层级 / isDir / 子项数 / 子树总大小 / 子树加密数 / 自己的 index（目录本身可能没有）`。
   纯函数意味着可以 `flutter test` 直接测（空包 / 单层 / 深嵌套 / 同名目录 / 带加密条目）。
2. **三态勾选**：目录节点 `全选 / 半选（横线）/ 未选`；勾目录 = 勾它下面所有文件；
   取消任一子项 → 父变半选。送引擎时**只送文件的序号**（目录不参与 `select`）。
3. **面包屑**：顶部显示 `包名 / 子目录 / …`，点某一级 = 只显示该层（真过滤，不是滚动定位），
   右侧一个「全部」回到根。理由：PeaZip 的面包屑是它被夸的点，7-Zip 的下拉框是被吐槽的点（`:682`）。
4. **状态栏常驻汇总**：`已选 N 项 · 共 M 项 · 合计 X`（PeaZip 的 `dir(s)/file(s)/size` 做法 `:631`）。
   半选状态的目录也要计入「已选」的直觉校验：**用文件的条数算，不用目录条数算**。
5. **列可配、默认带「压缩后大小」**：`EntryItem` 已有 `size`/`compressedSize`/时间，默认显示
   `大小 · 压缩后 · 时间 · 加密`，跟 PeaZip 一样把「压不动」的文件一眼看出（`:632`）。
6. **视图切换**：树 / 平铺两档，默认树；平铺保留给「只要全选」的老用户习惯。
7. **安全默认不变**：画树只用 `list` 的结果，**不为了预览去解压**（PeaZip 同款口径）。

### 边界（明确不做）

- 不做虚拟化/增量加载：条目数先按 ≤ 5000 直接渲染，超了再谈（现在没有 5000+ 的真实抱怨）。
- 不做「解压后树自动刷新」。
- 不做树内搜索（`--pick` 也没有，另立条目再说）。
- 目录本身若在归档里是**空目录条目**，树里显示但不可勾（没有内容可解）。

### 验收

- `flutter test`：树构建纯函数 6 组用例（空包 / 单层平铺 / 深嵌套 / 同名中间目录 / 加密计数 / 空目录不参与勾选）。
- 三态逻辑单测：勾父→子全选；取消一子→父半选；全选→`_picked` 数 == 文件数。
- 手工实测一个 ≥ 1000 条目的包：展开、勾选、面包屑切换无卡顿（**记录实测数字**，别写「流畅」）。
- 部分解压一致性：树上勾 3 个 → 产物只有这 3 个，且与命令行 `--select 1,3,5` 的产物 `sha256` 完全一致。

## B. 干扰数据 / 假签名（打包侧）

### 依据

- `refs/analysis/05-压缩布局验证.md` §2.1 的**布局矩阵**（L1 尾部追加 / L2 尾部 free 原子 / L3 ftyp 后 free /
  L4 插在中间 / L5 分散多段 / L6 前后加垃圾）：其中 **L1 / L2 / L4 实测「封面视频能正常播 + 我们能逐字节解出」**。
- 同文件 §1.3 **资源红线**：样本总量 ≤ 150 MiB、单样本 ≤ 30 MB、全程 1 MiB 分块流式（不许整包读进内存）。
- `refs/tech/sevenz-rust+steganographier.md` + `docs/REFERENCE-INDEX.md:37`：隐写者会**成批撒假的
  `Rar!` / `PK\x03\x04` / `\x1f\x8b` / `BZh` / `\xfd7zXZ` 特征码**，后面跟几 KB 随机数据，专骗扫描器。
- 同台账指出我们**已有防线**：`src/scan.rs` 的「1 MiB 头缓冲 → 候选队列 → **实际解析验证**」，
  所以假签名能糊别人、糊不了我们 —— 这正是可以放心加这个能力的前提。

### 现状

打包支持 `--layout L1|L2`（`src/pack_post.rs:84` 的分卷、`pack/mod.rs` 的外壳拼装），
但没有「噪声段 / 假签名」这个维度。

### 设计决策

1. **新参数**（都进 `src/cli_spec.rs` 唯一真源，跑生成器同步补全/man）：
   - `--decoy <n>`：撒 n 段干扰数据，默认 `0`（不打）。仅允许 `n ≤ 64`。
   - `--decoy-size <大小>`：每段字节数，默认 `16K`，范围 `4K–1M`（**默认值要小**，见第 5 条）。
   - `--decoy-signatures <on|off>`：每段里是否夹一枚假特征码，默认 `off`。
2. **只允许两种布局**：尾部追加（L1）与尾部 `free` 原子（L2）。矩阵里 L1/L2 实测 ffmpeg 无解码错误；
   L3/L4/L5 要动盒子结构或拆成多段，收益低、风险高，**不做**。
3. **噪声位置铁律**：全部写在**压缩数据之后、外壳逻辑之外**的位置（L1：ZIP 之前；L2：`free` 原子数据段里
   `PK\x03\x04` 之前）。**绝不写进 MP4 box 本体、绝不写进压缩流内部** —— 前者会破坏播放，后者会破坏解压。
4. **假签名只撒在噪声段内**，候选集固定（`Rar!`、`PK\x03\x04`、`\x1f\x8b\x08`、`BZh`、`7z\xbc\xaf\x27\x1c`），
   每段最多一枚，后面跟**随机字节**（不是零）。
5. **可复现**：随机量用 `stable_seed(输入路径 + 段号)` 的固定种子（`refs/analysis/05:75` 的教训：
   不能用 `hash()`，它受 `PYTHONHASHSEED` 影响）。**同一份输入两次打包逐字节一致** ——
   与隐写者「每次哈希都变」的做法相反，因为用户要能校验自己下载的东西。
6. **不破坏「看起来是媒体」**：噪声总长默认 ≤ 外壳大小的 10%，且以零填充为主、假签名点缀。
   依据是矩阵 L6 的教训：前后加 5 MiB 垃圾后 `file` 把产物认成了 `OpenPGP Public Key`（`:2.1 表末行`）。
7. **打完自检**（打包流程内置，不是可选）：
   - 产物里能重新定位到 EOCD / 压缩包起点；
   - 用引擎自己 `--test` 跑一遍（本轮刚做好的只测不写）**必须通过**；
   - 解出的内容与未加干扰的版本 `sha256` 一致（噪声不参与解压）。
   任一条不过 → 打包判失败并**删除产物**（不留半成品）。

### 边界（明确不做）

- 不做 L5「分散多段」（那是解包方向的能力，打包侧把包拆散会让别人的工具也解不了，等于坑用户）。
- 不做「假签名伪装成另一种压缩格式的完整包」（会让人误以为里面有两层，属于骗人）。
- 不加「随机每次不同」的模式（可复现优先，见决策 5）。
- 不碰任何法律边界的用途宣传：这是给用户**给自己的东西**加干扰、躲网盘误判用的（README 口径同「本工具不做的事」一节）。

### 验收

- 单元测试：`--decoy 4 --decoy-signatures on` 打包后 —— EOCD 仍可定位、ZIP 起点可定位、
  解出的 ZIP 与未加干扰版本 `sha256` 一致、两次打包逐字节一致（可复现）。
- 探针 `tests/decoy.sh`：`yshjy --decoy 4` 打包 → `yshjy --list` / `7z l -t#` / `unzip -l` 都能列内容；
  `file` 仍认成媒体（不是 OpenPGP/未知）；`yshjy --test 产物` 通过。
- 资源红线：样本总量与峰值内存按 `05 §1.3` 的口径记录（流式、≤ 30 MB/样本）。

## C. 移动端 seek 三档

### 依据

- `docs/ARCHITECTURE.md:344` F1：「手机端存储可能不支持 seek → 三档方案：① 直接 fd 路径 ② 块缓存
  ③ 兜底先复制到私有目录（须先做空间预检）；**选文件后立即探测 seek 能力**」。
- `docs/REFERENCE-INDEX.md:103`：状态 ❌ 待做。

### 现状

桌面侧全部走 `Read + Seek`（`Source` 抽象），没有「不可 seek 怎么办」这一层。

### 设计决策（本轮只做前三件，落地留 Android 批）

1. **探测函数**：`hardware::seek_ability(path) -> SeekAbility { Full, BlockCache, CopyFirst }`。
   实现：尝试 `seek(SeekFrom::End(0))` + 回到原位；失败再试探 `SAF` 常见的「只能顺序读」特征。
   单测用普通文件（应为 `Full`）+ 只读打开/管道（应为降级档）覆盖。
2. **块缓存适配器**：`io::BlockCache<R>`，32 KiB 块、LRU 8 MiB 上限，实现 `Read + Seek`。
   给不支持 seek 的源套上，**解码逻辑一行不改**（和本轮 `PartFile` 的 sink 模式同一个思路：
   把差异收在 IO 层）。
3. **协议暴露**：`scan` 的每个候选加一项 `seek: "full"|"block_cache"|"copy_first"`；
   `hello.formats` 之后另加 `seek_probe: true` 能力位。界面据此给该文件打标记并提示
   「这个位置不能跳着读，会先复制一份（占 X MB）」。
4. **复制兜底**：真到 `CopyFirst` 时先跑空间预检（复用 `safety::check_space`），
   空间不够**明确报错**而不是静默失败（这是 F1 的原话）。

### 边界

- **本机没有 Android 环境**（`Wayland` 桌面、无 Android SDK 设备），所以「SAF 到底算哪一档」**不下结论**：
  本轮只把探测与降级做成可单测的代码 + 协议字段，**落地验收写进 Android 那批的清单**，不冒充已完成。
- 不做「边下边解」的流式适配（`zip` crate 需要 seek，这是另一条路）。

### 验收

- 单测：`seek_ability` 对普通文件返回 `Full`；对 FUSE/管道之类返回降级档（用 `/dev/stdin` 或 `pipe` 造）。
- 块缓存单测：随机 `seek + read` 序列与「整读进 Vec 再切」逐字节一致；超过 8 MiB 时 LRU 真的丢块（断计数）。
- 协议：`scan` 结果里有 `seek` 字段，`hello` 有 `seek_probe: true`。
- **Android 待验清单**（写进 `docs/TODO.md` 平台节）：SAF 打开的 `content://` 走哪一档、复制兜底的预检数字。
