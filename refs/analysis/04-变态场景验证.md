## 1. 我们的方案（被测对象）

Python 侧（`tests/extreme_tests.py`）与 Rust 侧（`spike/src/bin/zip_extreme.rs::Ranges`）实现的是**同一套四步算法**，对应设计要求里的「全文件签名扫描 + 偏移修正 + Concat 虚接 + 无目录表傅底」：

1. **全文件流式签名扫描**：1 MiB 分块 + 3 字节重叠，记录所有 `PK\x03\x04`(LFH)/`PK\x01\x02`(CDFH)/`PK\x05\x06`(EOCD) 的**绝对位置**。峰值内存与文件大小无关。
2. **偏移修正 + 起点搜索**：对每个 EOCD 候选算出朴素起点 `EOF−size_cd−offset_cd`，再**在真实 LFH 里搜起点**；起点不可信时以「虚接后能否全过 CRC」为准。
3. **Concat 虚接（Ranges/SplicedIO）**：把「不连续但在逻辑上连续」的若干区间拼成一个 `Read+Seek` 逻辑流，直接交给标准 `zip` crate / `zipfile`。**不落临时文件、不整包读入内存**。
4. **无目录表傅底（救援模式）**：只按 local header 顺序扫描，逐条解压 + CRC32 校验。

## 3. 逐场景实测（真实输出）

### 3.1 E1　[垃圾 5MiB][ZIP][垃圾 5MiB]

```
$ spike/target/release/zip_extreme tests/data/E1_junk5m_zip_junk5m.bin
   file_len=10498640  扫描命中: LFH=6 CDFH=6 EOCD=1  (峰值内存 VmHWM:  4248 kB)
   [对照 naive ZipArchive::new(File)] 打开失败: invalid Zip archive: Could not find EOCD
── EOCD @ 5255738 (距EOF 5242902) entries=6 size_cd=378 offset_cd=12480 comment=0
   朴素推算 ZIP 起点(EOF−size_cd−offset_cd)=5242880
   ✅ 起点 LFH @5242880（Δ=0）: 虚接 + zip crate 打开成功 entries=6 CRC 全过 6/6
      段=[(5242880, 12880)]  保留=12880  跳过(洞/插入)=0
```
```
$ python3 -m zipfile -l tests/data/E1_junk5m_zip_junk5m.bin
zipfile.BadZipFile: File is not a zip file          # rc=1
$ unzip -l tests/data/E1_junk5m_zip_junk5m.bin
...  rc=9
$ 7z l tests/data/E1_junk5m_zip_junk5m.bin          # rc=0，Warnings:1；7z x rc=0 解出 6 文件
```
**结论**：**能**。EOCD 距文件尾 5 MiB → `zipfile`（只搜尾部 64 KiB）与 `zip` crate 的 `Detect`（`Could not find EOCD`）**都失败**；7-Zip 能过。我们的**全文件扫描**命中并虚接成功。救援模式也 100% 恢复。
**极限**：垃圾里若混入**伪 EOCD**（合法 22 字节，如 apate 风格的假签名），会把我们引向错误候选。本样本 5 MiB 随机垃圾没撞出伪 EOCD（概率 ≈ 5e6/2³² ≈ 0.1%），但**必须用「虚接后能否 CRC 全过」筛掉伪候选**，否则会解出空包或报假成功。

### 3.2 E2　[视频前半][ZIP][视频后半]

```
$ zip_extreme tests/data/E2_video_split_zip_middle.mp4
   [对照 naive ZipArchive::new(File)] 打开成功 entries=6  CRC 通过 6/6
   ✅ 起点 LFH @15214（Δ=0）: 虚接 + zip crate 打开成功 entries=6 CRC 全过 6/6
      段=[(15214, 12880)]  保留=12880  跳过(洞/插入)=0
```
`tests/extreme_video_check.py` 实测视频：
```
原视频 ev10.mp4          size=30429 ffmpeg_rc=0    sha256=7e8bbc08af5dd700
E2 样本(含 ZIP)          size=43309 ffmpeg_rc=183  ['moov atom not found', ...]
拼回(去掉 ZIP)            size=30429 ffmpeg_rc=0    sha256=7e8bbc08af5dd700
拼回 === 原视频 ? True
仅视频前半                size=15214 ffmpeg_rc=183  ['moov atom not found']
仅视频后半                size=15215 ffmpeg_rc=0    ['warning: first frame is no keyframe','header damaged']
```
**结论**：**能**。ZIP 完整嵌在视频中间 → 虚接直接成功。
**「视频切开后拼回还能播吗」的答案：能，且是逐字节无损**（拼回 sha256 与原视频完全相同、`ffmpeg rc=0`）。而**直接拿着 E2 当视频播：不行**（`rc=183 moov atom not found`，因为插入的 ZIP 打断了 MP4 原子链）。→ 这对我们「还原视频」功能是有用的事实：**只要能定位并摘掉 ZIP 段，封面视频就能无损复原**。

### 3.3 E3　[ZIP前半][视频][ZIP后半]（切点=成员边界）

```
$ zip_extreme tests/data/E3_zip_split_by_video.mp4
   朴素推算 ZIP 起点(EOF−size_cd−offset_cd)=18164        ← 注意：这个朴素值是错的！
   ✅ 起点 LFH @0（Δ=-18164）: 虚接 + zip crate 打开成功 entries=6 CRC 全过 6/6
      段=[(0, 12290), (30454, 590)]  保留=12880  跳过(洞/插入)=18164
```
harness：`[我们的方案] ✅ 虚接段=[(0,12290),(30454,590)] 跳过=18164 → entries=6 CRC 6/6`，`[救援模式] 6/6 = 41,200/41,200 B (100%)`。
**结论**：**能，一次成型**。算法从第一条 LFH 按“成员长度”走到 `12290`，发现下一个位置不是 PK 签名 → 判定这是插入段 → 向后找到下一条 LFH（`30454`）→ 虚接 `[0,12290)` + `[30454, EOF)`，**正好复原原始 ZIP**，6/6 CRC 全过。
**关键坑**：`EOF−size_cd−offset_cd` 在有内部插入时**给出的是「插入长度」而不是「起点」**（这里是 18164，真实起点是 0）。任何拿这个值当起点的实现都会踩空 —— 必须用真实 LFH + 虚接校验确定起点。

### 3.4 E3b　切点落在**成员数据内部**（这是 E3 的狠版，也是本报告最重要的极限）

```
$ zip_extreme tests/data/E3b_zip_cut_inside_member.mp4
   朴素推算 ZIP 起点(EOF−size_cd−offset_cd)=18164
   ❌ 全部 6 个 LFH 候选虚接后都无法全过 CRC。最好一次: 起点 @0 entries=6 CRC 5/6
      段=[(0, 12290), (30454, 590)]  跳过(洞/插入)=18164
   ✔ payload/r1_a.txt 6000 B CRC OK
   ✔ payload/r2_b.bin 6000 B CRC OK
   ✔ payload/r3_c.txt 11000 B CRC OK
   ✘ payload/r4_d.bin 读数据失败: Invalid checksum      ← 被切断的成员
   ✔ payload/r5_e.txt 6000 B CRC OK
   ✔ payload/中文_名.txt 6200 B CRC OK
```
因为 `r4_d.bin` 的数据横跨视频，“单纯虚接”会把视频字节当成它的数据 → CRC 失败。
我们的**插入建模 + CRC 引导搜索**（`extreme_tests.py::resolve_insert`）命中：
```
[插入建模] ✅ 切点 a=9264 m=18164 被切断成员=payload/r4_d.bin 搜索 2980 次 → entries=6 CRC 6/6
```
**结论**：**有条件**。判据是：**CD（中心目录）完好** → 从 CD 拿到每个成员的 `lho/csize/crc`；按**成员名**在文件里重新定位每条 LFH 的物理位置 → 得到 `shift ∈ {0, m}` 的前/后两段 → 被切断成员的数据区间 `[data_start, 下一成员lho]` 内**逐字节试切点 a**，用**这条成员自己的 CRC32** 判定。本例窗口 ~6000 字节、搜索 2980 次（毫秒级）。
**极限**：
- **加密包没有可用 CRC**（ZipCrypto/AES 的 CRC 要么为 0、要么被替换）→ 搜索判据失效 → **无法定位切点**，只能退到「按成员粒度救援」。
- **被切成多段**（多处插入）→ 搜索空间随段数组合爆炸。
- **CD 也被破坏** → 连「成员名/lho」都拿不到 → 退到救援模式。

### 3.5 E4　中间段被**真替换**（丢数据）

```
$ zip_extreme tests/data/E4_zip_middle_overwritten.mp4
   扫描命中: LFH=5 CDFH=6 EOCD=1        ← 只剩 5 条 LFH（第 4 条被视频覆盖了）
   [对照 naive ZipArchive::new(File)] 打开成功 entries=6  CRC 通过 5/6
   朴素推算 ZIP 起点(EOF−size_cd−offset_cd)=0
   ❌ 全部 5 个 LFH 候选虚接后都无法全过 CRC。最好一次: 起点 @0 entries=0 CRC 0/0
      段=[(0, 6239), (12290, 590)]  跳过(洞/插入)=6051
   ⇒ 判定：结构自洽性被破坏 = 真丢数据 → 走救援模式
```
harness 救援：`[救援模式] 找到 5 个 LFH → 恢复 5/6 成员 = 35,200/41,200 B (85.4%)`。
`[插入建模] ❌ 跨度(12880)<=逻辑长度(12880)，非插入场景` ——**系统正确地识别出「E4 不是插入、而是等长替换」**（跨度正好等于逻辑长度，`m=0`）。
**结论**：**不能完整解开**，只能救出未受损成员 = **85.4%**（5/6 成员）。丢失的 `r4_d.bin` 连 LFH 都没了，救援扫描**找不到它**（所以「失败项=[]」，但成员数从 6 掉到 5）。
**极限**：**丢失段覆盖多少成员就永久丢多少**；若替换段恰好覆盖了 CD/EOCD，则连「一共有几个成员」都不知道，救援只能报「找到 N 个」。
**救援模式能做的**：① 逐条 CRC 校验，把「解出来但 CRC 不符」的成员**明确标为不可信**（不静默当成功）；② 报告恢复了哪些、丢了几条；③ 对 stored/deflate 成员逐字节抢救。

### 3.6 E5　头尾各切一块（截断）

```
$ zip_extreme tests/data/E5_zip_headtail_truncated.zip
   扫描命中: LFH=5 CDFH=4 EOCD=0
   [对照 naive ZipArchive::new(File)] 打开失败: invalid Zip archive: Could not find EOCD
   ✗ 全文件找不到 EOCD（尾部被截断？）→ 只能走救援模式（无目录表）
```
harness：`[救援模式] 找到 5 个 LFH → 恢复 5/6 成员 = 35,200/41,200 B (85.4%)`。
**结论**：**有条件**（EOCD/CD 丢失 → 只能救援）。本例头部丢了第 1 个成员（`r1_a.txt`）、尾部丢了 EOCD，中间 5 个成员完好 → 救出 5/6。
**极限**：**头尾被切掉的成员全丢**；**没有 CD 就无法知道原始有几个成员** —— 只能报「找到 5 条 local header」，用户无法判断是否完整。7-Zip 同样只能靠 local header 救援（`7z x` rc=2 但写出 5 个文件）。

### 3.7 E6　一个文件里藏**两个不同的压缩包**

```
$ zip_extreme tests/data/E6_two_zips.mp4
   扫描命中: LFH=9 CDFH=9 EOCD=2
── EOCD @ 35452 … entries=3  ✅ 起点 LFH @31044: 虚接成功 entries=3 CRC 3/3   ← ZIP2
── EOCD @ 12858 … entries=6  ✅ 起点 LFH @0:     虚接成功 entries=6 CRC 6/6   ← ZIP1
```
两个包**都被找出来了**。对照常规工具：
```
$ 7z l E6_two_zips.mp4     → 6 files（payload/r1_a.txt…中文_名.txt）  ← 只找到 ZIP1
$ 7z x E6_two_zips.mp4     → rc=0，解出 6 个文件（r1..中文_名）        ← 只找到 ZIP1
$ unzip -l E6_two_zips.mp4 → 3 files（q1.txt/q2.bin/q3_二.txt）        ← 只找到 ZIP2
$ python3 -m zipfile -l …  → q3_二.txt …                              ← 只找到 ZIP2
```
**关键发现**：**7-Zip 只找到第一个包，unzip/python 只找到最后一个包，没有任何一个常规工具把两个包都列出来。** 这是我们相对于所有常规工具的核心差异化点。
**极限**：两个包若**共用同一段字节**（嵌套/重叠），或第 2 个包**没有自己的 EOCD**，则无法完整枚举。当前只支持「各自有独立 EOCD」的多包。

### 3.8 E7　多个穿插 `[视频][ZIP1][视频][ZIP2]`

```
$ zip_extreme tests/data/E7_vid_zip_vid_zip.mp4
   扫描命中: LFH=9 CDFH=9 EOCD=2
   ✅ EOCD@65881 起点LFH@61473 段=[(61473,4430)]  entries=3 CRC 3/3   ← ZIP2
   ✅ EOCD@43287 起点LFH@30429 段=[(30429,12880)] entries=6 CRC 6/6   ← ZIP1
```
**结论**：**能**，两个包都找出，且不受前后视频干扰。7z 同 E6 只找到 ZIP1（`7z x` 6 文件）。

|---|---|---|---|---|---|---|---|
| E1 | 0 | 0 | 0 (6 文件) | 9 | 9 | 1 | 1 |
| E2 | 0 | 0 | 0 (6) | 1 | 1 (无错) | 0 | 0 |
| E3 | 2 | 2 CRC错 | 2 (4 文件) | 1 | 4 | 0 | 0※ |

| E5 | 2 | 2 | 2 (5) | 9 | 9 | 1 | 1 |

| E7 | 0 (只 Z1) | 0 | 0 (6, 只 Z1) | 1 | 1 | 0 (只 Z2) | 0 |

※ **重要陷阱**：`python3 -m zipfile -t` **退出码恒为 0**，即使它打印了 `The following enclosed file is corrupted: 'payload/r4_d.bin'`。实测 E3/E4 都是 rc=0 但明确报错。**绝不能拿 `zipfile -t` 的 rc 当判据**（7z 的 rc 反而更靠谱）。
另一条：`7z l -t#`（关掉类型探测）对所有样本都「成功」但列出的 `3 files / 10498640` 之类似的**是把它当裸流**，**没有判断价值**，不要用它。
再一条（DESIGN 已记录，这里复现）：`7z x` 在 rc≠0 时**仍会写出文件**（E3/E4/E5 都写出 4~6 个）。判「有没有解出东西」必须**对比输出目录快照**，不能看 rc。

| **我们的方案（Python 探针，含扫描 10MB 的 E1）** | **22.8 MiB**（`harness_peak_rss_kb=22844`） | 全流式；与文件大小无关 |
| **我们的方案（Rust `zip_extreme`，E1=10MB）** | **4.2 MiB**（VmHWM 4248 kB） | `Ranges` 虚接 + zip crate 流式解 |
| Rust `zip_extreme`，其余小样本 | 2.3 – 2.9 MiB | — |
| `7z l/t/x`（子进程） | ~13.5 – 13.9 MiB | 每个命令 fork+`wait4` 取 `ru_maxrss` |
| `unzip`（子进程） | ~14.1 – 14.4 MiB | 同上 |
| `python3 -m zipfile`（子进程） | ~14.2 MiB | 同上 |
| `free -h` 测试前 / 后 | used 5.2 Gi → 5.4 Gi | 差异在噪声内；**峰值内存与文件大小无关**（解 10 MB 文件只花 ~4–23 MB） |

**内存结论**：扫描 / 虚接 / 救援**全程流式**，10 MB 文件峰值仅 4–23 MiB，**没有一处 `read_to_end` 整包读入**。这条设计（`Concat`/`Ranges` 纯 `Read+Seek` 包装器）在变态场景下依然成立。

## 6. 「我们必须在代码里实现的防护清单」

针对以上场景，正式版 yshjy **必须**实现（按重要性排序）：

1. **全文件流式签名扫描**（不是只读尾部 64 KiB）。分块 1 MiB + 3 字节重叠，只记签名位置、不载入数据。→ E1/E6/E7。
2. **EOCD 候选逐个独立处理，且要枚举全部**，不能只取最后一个。→ E6/E7（常规工具全部漏掉一个）。
3. **起点不能用 `EOF−size_cd−offset_cd` 当唯一依据**：有内部插入时它给的是「插入长度」。必须以**真实 LFH + 虚接校验**确定起点。→ E3/E3b。
4. **虚接必须以「全成员 CRC 全过」为成功判据**；不能全过 = 真丢数据 → 转救援。这是 **E3（可救）与 E4（不可救）的唯一判别器**。
5. **插入建模 + CRC 引导搜索**：切点未知时，从 CD 反查每个成员的物理 LFH → 得到 `shift ∈ {0, m}` 的前/后两段 → 在被切断成员的 `csize` 窗口内逐字节试切点、用该成员自身 CRC 判定。**必须设搜索步数上限**（防大成员导致卡死）。
6. **无目录表救援模式**：只按 local header 扫描 + CRC32；必须**明确报告**「恢复了哪些 / 丢了几条 / 哪些 CRC 不符（写了但不可信）」——**绝不能静默当成功**。→ E5/E4/D 组。
7. **多包枚举**：把所有自洽的包**全部**列出来交用户选，不能只返回第一个。→ E6/E7。
8. **报错语义要区分**：缺卷 ≠ 截断 ≠ CRC 错 ≠ 结构自洽性破坏；且**任何工具的 exit code 都不能单独作为判据**（实测 `python zipfile -t` 恒为 0，`7z x` rc≠0 仍写文件）。
9. **内存护栏**：扫描/虚接/救援全流式（禁止整包 `read_to_end`）；单包解压放子进程 + `RLIMIT_AS`（沿用 `03-技术验证.md` §2.5 的结论）。
10. **伪签名过滤**：前置/尾部垃圾里的伪 `PK`/伪 EOCD 必须用「虚接后能否全过 CRC」筛掉，否则会解出空包或假成功。

**明确搞不定的（要在 UI 上诚实告知用户）**：
- **E4 型真丢数据**：丢失段内的成员**永久不可恢复**，只能给「救出 N 个」。
- **E5 型无 EOCD 截断**：**无法知道原始成员总数**，只能报「找到 N 条 local header」。
- **E3b 型加密包内部切断**：无 CRC 可校验 → **无法定位切点**，退到成员粒度救援。
- **多个包共用字节 / 第二个包无独立 EOCD**：无法完整枚举。
