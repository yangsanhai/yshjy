# A. 软件工程师视角

## A1 🔴 架构设计文档（最缺，优先级最高）
现在"三层架构"只是一个概念图。真正动手前必须有：
- **模块划分**：crate 结构（单 crate 还是 workspace？core/cli/gui 怎么切）
- **接口定义**：核心数据结构（如 `Layout` / `ArchiveInfo` / `Task`）、trait 边界（`Scanner` / `Extractor` / `PasswordProvider`）
- **数据流管线**：输入 → 识别 → 定位 → 提取 → 解压 → 校验 → 报告，每步的输入输出
- **并发与进度模型**：进度回调怎么穿透各层？要不要多线程（解压/哈希并行）？
- **状态机**：任务从"排队"到"完成/失败/取消"的状态流转
- **错误类型体系**：哪些可恢复、哪些要用户介入、哪些直接放弃

> ⚠️ 不写架构就动手 = 大概率返工（我们已经有 20 份报告的知识量，更需要先设计再写）

## A2 🔴 状态设计（功能级别）
我们定义了大量功能（解压/压缩/救援/预览/密码/分卷/嵌套…），但**没有定义每种状态的行为**：
- 加载中 / 成功 / **部分成功** / 失败 / 需要密码 / 需要用户选择 / 被取消
- "部分成功"（救援模式救出 85%）在界面上怎么呈现？（这是我们的特色功能！）
- 多任务并发时的状态聚合

## A3 🔴 测试自动化 + CI
- 已有 **59 个测试样本**（35 基础 + 8 变态 + 16 布局）→ 必须变成**自动化回归套件**
- 缺：单元测试框架约定、集成测试如何跑全样本、性能基准（bench）
- 缺：CI（GitHub Actions）——每次提交自动跑全部样本
- 缺：`cargo-deny`（依赖许可证审计，我们要求"只用开源"）

## A4 🟠 安全设计（已识别，未具体化）
报告里发现的隐患还没变成设计条目：
- **Zip Slip**（路径穿越）：解压时路径必须规范化，拒绝 `../` 和绝对路径
- **符号链接攻击**：包内软链接指向外部文件
- **zip bomb / 内存耗尽**：7z 库的内存限制形同虚设 → 必须自建护栏
- **解出可执行文件的提示**（这类资源是恶意软件重灾区）
- **临时文件权限**（明文解压内容不能是 0777）

## A5 🟠 工程规范与工具链（全缺）
```
✗ LICENSE            （许可证，建议 MIT）
✗ README.md          （门面，中文优先）
✗ CONTRIBUTING.md    （别人想帮忙怎么办）
✗ CHANGELOG.md       （版本变更记录）
✗ rustfmt.toml       （代码风格统一）
✗ clippy.toml        （静态检查规则）
✗ deny.toml          （依赖许可证/漏洞审计）
✗ .github/workflows  （CI/CD）
```

## A6 🟠 构建与发布策略
- 目标平台：x86_64 linux（gnu/musl？）、后续 Windows/Android 的交叉编译方案
- 产物格式：`.deb` / AppImage / tar.gz？（用户偏好 deb > Flatpak）
- 版本策略：semver，v0.1 什么时候发、发到哪
- 依赖策略：锁定版本（Cargo.lock 提交）、最小依赖、审计

## A7 🟠 GUI 技术选型（还是没定！）
Flutter vs egui（纯 Rust）—— 这个决定影响工程结构，越早定越好：
| | Flutter | egui |
|---|---|---|
| 覆盖 | 桌面+移动 5 平台 | 桌面为主，移动不成熟 |
| 语言 | Dart + FFI 桥 | 纯 Rust（单二进制） |
| 用户基础 | **用户有 Flutter 基础** ✅ | 需要学 |
| 包体积 | 大 | 小 |

## A8 🟡 配置系统
- 密码本存哪？（`~/.config/yshjy/` 还是跟随项目目录）
- 用户偏好（默认布局、默认密码本、语言）
- 配置格式（TOML/JSON）、向后兼容策略

## A9 🟡 可扩展性设计
- **格式插件化**：以后加新格式/新伪装变体，不该改核心代码
- **布局规则化**：L1~L8 应该由"规则描述"驱动，而不是硬编码分支
- 这也是应对"隐写者升级格式"的必要手段

## A10 🟡 日志与诊断
- 用户报障时怎么给信息？→ 建议：`--report` 导出一份"诊断包"（环境+参数+日志+关键偏移）
- 日志分级（静默/正常/调试）

## A11 🟡 性能与资源预算（有实测数据，但没定标准）
- 内存上限：实测流式仅 4~27MB → 定为"解 8GB 不许超 64MB"
- 临时空间策略：明确什么时候需要临时空间、需要多少
- 并发度：i5-8250U 8 线程，解压/哈希可否并行

## A12 🟢 国际化（先不做，但留口子）
中文优先，但文案不要硬编码在代码里（便于以后加英文）

# B. 设计师视角

## B1 🔴 只设计了"成功路径"（最缺）
现有界面草图全是"一切顺利"的流程。但真实使用中大量是异常：
```
· 解压到一半发现需要密码 → 界面长什么样？
· 只救出 85% → 怎么表达"部分成功"才不让用户恐慌？
· 文件损坏到无法识别 → 说人话的同时要有"下一步建议"
· 磁盘不够 → 提前警告的界面
· 用户选错模式（压缩当成解压）→ 怎么友好纠正
· 解压出 351 个文件 → 界面怎么展示不刷屏
```
**这些"非顺利状态"的界面一个都还没有。**

## B2 🔴 文案系统（一句都没写）
"说人话"是我们明确的核心卖点，但目前：
- 所有用户可见文字（进度、错误、引导、按钮）都还没写
- 语气不统一（是亲切还是专业？建议：亲切但不幼稚）
- 需要一份"文案表"：每个状态说什么，含"人话版 + 技术细节折叠"

## B3 🔴 竞品界面参考（完全空白）
我们研究了 37 个工具的功能，但**没有看过任何一个的界面**。
→ 至少要看：Complex-unzip-tool-v2 / Bandizip / ZArchiver / 解TMD压 的截图，
   学它们的信息层级与操作流（尤其手机端）

## B4 🟠 视觉设计语言
```
✗ 配色（主色/状态色/暗色模式）
✗ 图标风格（是 emoji 还是线性图标？emoji 跨平台不一致！）
✗ 字体与字号层级
✗ 间距/圆角/阴影规范
✗ Logo / 品牌视觉（GitHub 头像、README 头图）
```
⚠️ 特别注意：现在草图用了大量 emoji（📦🔒⚠️），但**手机上 emoji 渲染差异大**，需要定策略

## B5 🟠 桌面 GUI 完整布局
手机端草图有了，但桌面端只有一句话描述（"拖进来 → 列表 → 单击/右键"）：
- 主窗口布局（列表区/操作区/状态区怎么摆）
- 设置页、密码本管理页、历史记录页
- 拖拽的交互反馈

## B6 🟠 完整用户流程图（含异常分支）
需要一张"全路径流程图"：从打开软件到任务结束，含所有分支与返回路径。

## B7 🟡 Onboarding 具体脚本
"首次启动弹窗介绍"——弹什么？分几步？每步说什么？
建议：3 屏（能做什么 / 怎么用 / 试试拖个文件进来）

## B8 🟡 组件规范
列表项、按钮、对话框、进度条、徽标（如 `🔒 有密码`）的一致性定义

## B9 🟡 帮助与文档体系
- 内置帮助（`yshjy --help` 的输出本身就是设计物）
- FAQ（"解不开怎么办"、"密码忘了"、"为什么和 WinRAR 结果不一样"）
- 一份面向小白的图文教程（用于社区传播）

## B10 🟢 无障碍 / 可访问性
键盘操作、屏幕阅读器、色盲友好（红色/绿色不能是唯一区分手段）

## B11 🟢 品牌与传播物料
- GitHub 仓库视觉（README 头图、徽章）
- 一段 15 秒的演示 GIF（"拖进去 → 解出来"，最有说服力的传播素材）
