# 一、🔴 最关键的问题（3 个）

## 问题 1：文案归属矛盾（我自己设计里的 bug）

**矛盾点**：
```
ARCHITECTURE.md 说：  「引擎不打印任何东西（日志/文案由外壳决定）」
BACKEND-SPEC.md 说：  「用户文案集中在 report.rs 管理」

→ 两句话打架：文案到底在引擎里还是外壳里？
```

**为什么这是问题**：
- 如果文案在 Rust 引擎里 → Flutter 要通过 FFI 传中文过来再显示，**白白浪费**，
  而且以后加英文版要改引擎重新编译；
- 如果文案在外壳里 → CLI 和 GUI **各写一遍**，容易不一致。

**✅ 正确设计（必须修正）**：
```
引擎：只产出「错误码 + 结构化参数」，绝不产出面向用户的中文句子
      例：Err(NeedPassword { entries: 351, encrypted_names: true })

外壳：
  CLI    把错误码渲染成终端文案（中文白话 + emoji）
  GUI    把错误码渲染成界面组件（图标 + 标题 + 建议 + 按钮）
  共用   一份「文案映射表」放外壳侧共享文件（Rust 里作为 CLI 的资源，
         Flutter 里作为 i18n 资源，内容保持一致但各自管理）
```

**代价**：文案表要维护两份（CLI 一份、GUI 一份），但换来的是：
- 引擎保持纯净（可测、可复用、无 UI 依赖）
- 以后加英文只改外壳
- 手机端不需要通过 FFI 传大段中文

## 问题 2：Android 存储不支持"随机定位"（会影响手机端可行性）

**背景**：
- ZIP/7z 解析**必须**能跳到文件尾读目录表（不是顺序读）
- 但 Android 的 SAF（文件选择器给的 URI）返回的流，**很多不支持 seek**
  （尤其是云盘 App 提供的流，如百度网盘、Google Drive）

**后果**：手机端"直接选文件就处理"可能直接失败

**✅ 解决方案（三档，按情况使用）**：
```
① 首选：文件在本机存储 → 用文件描述符（fd）打开，支持 seek ✅
② 备选：不支持 seek 时 → 分块读取 + 自建「块缓存」
         （记录已读块，seek 时从缓存取或重新读）
③ 兜底：先完整复制到应用私有目录再处理
         （代价：需要额外一份空间；8GB 文件要 16GB 空间 → 必须先做空间预检）
```
**设计要点**：引擎的 `ReadSeek` trait 本来就能容纳这三种实现
（这正是当初把 I/O 抽象成 trait 的价值 ✅）。

**需要补的**：v0.5 之前必须实测"百度网盘 App 分享过来的文件能不能 seek"。

---

## 问题 3：Rust → Android 的构建链从未验证过

**现状**：
- 我们验证了三个 Rust 库能在 **Linux 桌面**跑 ✅
- 但**从没验证过** Rust 能交叉编译到 Android、并被 Flutter 调用

**风险**：
- 如果 `sevenz-rust2` / `rars` 有 C 依赖或平台特定代码 → 手机端可能编不过
- NDK 版本、cargo-ndk、FRB codegen 的配合问题

**✅ 建议**：
```
v0.1 完成后（不要太晚），做一次最小验证：
   Rust 函数「返回一个字符串」→ 编译成 Android .so → Flutter 调用 → 显示出来
只要这条链通了，后面就是加功能；不通就趁早换方案（比如手机端改用 Kotlin 原生）。
```

# 二、后端（引擎）层 —— 4 个待修

## B1 🟠 取消不及时（用户点了取消要等很久）
**问题**：解压库内部的循环不受我们控制（7z 解一个大文件可能几十秒不返回），
此期间 `AtomicBool` 检查不到。
**✅ 方案**：把取消检查**下沉到 Reader 层** ——
包一个 `InterruptibleReader`，每读 1MB 检查一次取消标志并返回 `io::Error`，
让库自己因为读失败而中断。

## B2 🟠 试密码会污染输出目录
**问题**：错误密码有时会"解出"一部分垃圾数据，写进输出目录 → 用户看到一堆乱文件。
（这是隐写者的已知坑：错密码留下垃圾文件污染后续判断）
**✅ 方案**：
```
两步走：先「验证」再「解压」
  验证阶段：只解第一个条目的第一个数据块，验证 CRC/校验值
  验证通过：才开始真正解压到目标目录
验证阶段的所有产物写到临时区，失败即丢弃
```

## B3 🟠 校验与解压重复读一遍（性能浪费）
**问题**：架构里说"v0.1 简化：解压后再单独跑校验" → 8GB 文件要读两遍。
**✅ 方案**：**边解压边算哈希**（`HashingWriter` 包装输出流，写入时增量更新），
单次 I/O 完成，8GB 文件省一遍完整读取。

## B4 🟡 虚接（SegmentReader）的随机访问性能
**问题**：数据被分成多段时，频繁 seek 会导致反复定位（每次 seek 都要找段）。
**✅ 方案**：
```
构造时建立「段索引表」（按起始偏移排序）
seek 用二分查找定位目标段
对顺序读做「段内指针缓存」，避免重复定位
并在日志里记录 seek 次数（用于性能诊断）
```

# 三、前端（GUI）层 —— 3 个待修

## F1 🟠 手机端"选文件"的存储权限方案未定
UI 里写了"点 + 选文件"，但**没定用哪种方式**：
```
方案A：SAF（系统文件选择器）→ 兼容好，但可能不支持 seek（见问题 2）
方案B：申请存储权限，直接读路径 → 好用，但 Android 11+ 权限受限
方案C：混合 —— 优先直接路径，不行再退回 SAF
```
**✅ 建议**：C 方案；并在选文件后**立刻探测是否支持 seek**，不支持就走缓存/复制分支，
同时给用户明确提示（"这个文件需要先复制一份，会多占 8.2GB 空间，继续吗？"）。

## F2 🟡 进度事件跨语言传递的频率问题
**问题**：设计里进度节流 100ms，但 Flutter 的跨平台通道有开销，
高频事件（尤其解析 351 个文件时）可能卡顿。
**✅ 方案**：
```
· 进度用「合并推送」：100ms 内多次变化只发最后一次
· 列表类数据（351 条目）一次性批量传，不要逐条传
· 大数据用「共享内存 + 句柄」而不是 JSON 拷贝（v0.5 再优化，v0.1 不涉及）
```

## F3 🟡 引擎错误码 → 界面组件的映射表还没建
问题 1 决定了"引擎发码、外壳渲染"，那么需要一张**映射表**：
```
NEED_PASSWORD    → 图标 🔒 + 标题「这个包有密码」+ 输入框 + 建议文案
NOT_ENOUGH_SPACE → 图标 💾 + 标题「空间不够」+ 数字对比 + [换位置]
...
```
**✅ 方案**：在 UI-SPEC 里把每个错误码对应的**界面形态**写清楚（不只是文案），
作为 Flutter 实现的直接依据。

# 四、中间联通（桥接）层 —— 2 个待修

## M1 🟠 事件回调的线程安全
**问题**：Rust 引擎在工作线程里产出事件，Dart 侧只能在自己的 isolate 里更新 UI。
直接在任意线程调 Dart 回调 = 崩溃。
**✅ 方案**：
```
Rust 侧：事件先进「有界队列」（避免生产过快）
FRB 侧：用它的 Stream 支持（内部已处理线程切换）
Dart 侧：StreamBuilder 订阅 → 自动回到 UI isolate
取消：由 handle 控制，不由回调线程控制
```

## M2 🟡 "本地服务"方案是多余的（架构精简）
**问题**：ARCHITECTURE.md 提过"Flutter ↔ Rust 可走本地 HTTP 服务"，
但既然桌面和手机都走 FRB（同进程 FFI），**本地服务没必要**（还要开端口、处理安全）。
**✅ 修正**：删掉该备选，桥接方案统一为 FRB。
（保留一个例外：如果将来要做"远程/网页版"，再考虑。）

# 六、结论

**三层各自的设计是完整的，但"接缝处"有 3 个真问题：**
1. **文案归属**（我的设计矛盾）—— 必须修，否则 CLI 和 GUI 会打架
2. **Android 存储 seek**（可能让手机端做不出来）—— 必须提前设计
3. **Android 构建链未验证**（技术风险）—— 不能等到最后才发现

其余 6 个是"细节待修"，都可以在写代码时顺手处理。

**修正后，三层贯通没有任何阻塞性问题。**
