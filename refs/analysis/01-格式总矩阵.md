## 2. ⭐ 伪装包必须优先兼容的 Top 3（这是我们的主战场）

| # | 变体 | 谁在用 | 识别方式 |
|---|------|--------|---------|
| **1** | **尾部追加 ZIP/ZIP64 + concat 偏移修正** | 隐写者模式A、`copy /b`、PolyZip 大多数格式 | 尾部 EOCD → 算 concat → 逐个 LFH 加偏移 |
| **2** | **MP4 free 原子内嵌 ZIP** | 隐写者模式B、PolyFlix、PhantomMan | 遍历顶层 atom，找 `free` 且载荷以 `PK\x03\x04` 开头 |
| **3** | **MKV/WebM 附件轨 (Attachment)** | 隐写者 mkv 模式、mkvmerge 手工夹带 | 解析 MKV EBML，找 Attachments 元素 |

**明确无法支持**（原因已记录）：
- 像素/DCT/LSB/PVD 级隐写（纯隐写术，非打包）
- OpenPuff / OmniHide 等闭源专有格式
- 无密码的真加密包

## 3. 🚨 关键技术警示（血的教训）

### 3.1 **不能"见签名即认包"**
隐写者模式B **会故意撒假签名**（假 RAR/ZIP/GZIP/BZIP2/XZ 特征码 + 5–10KB 随机数据，源码 L2302-2320）。
→ 我们的扫描器必须：**签名命中后要真正解析确认**（能读出合法结构才算数），而不是见到 `PK\x03\x04` 就认。

### 3.2 隐写者 1.3.x 改过模式A，新老两种都要吃
- **老版**：ZIP 裸追加在尾部
- **1.3.x**：ZIP 包进**尾部 free 原子**，前置 64–256 B 随机填充
→ 尾部检测逻辑要同时兼容「尾部是裸 EOCD」和「尾部是 free 原子包着 ZIP」。

### 3.3 同名文件家族庞大，识别优先级要排好
unar 报告点出：9 个"过度热心探测器"会误判、7 个格式只看文件名、12 组"先手遮蔽"风险。
→ 借鉴 unar 的做法：**廉价 magic 检查排前、昂贵全文件扫描排后、识别期异常一律当"不匹配"**。

## 4. 🎯 重大新发现（超出既有情报）

### 4.1 apate 格式已被完全逆向 ✅
```
尾部 4 字节 = 小端整数 N
文件头存储在 [len-4-N, len-4) 区间，写入时是逆序的
→ 只需再逆序一次即可还原原始文件头（不是加密！）
```
**我们可直接支持还原 apate 文件，不需要 apate.exe。**（源码 Wiki 原本说"必须用对应软件"）

### 4.2 RAR 的许可难题解决了
`rars` 0.11.0（纯 Rust、Apache-2.0）支持 RAR 1.5 → RAR7 读取。
→ 只走读路径，即满足「RAR 只解不压」的红线，且不依赖非自由 UnRAR 许可。

### 4.3 中文圈真正的对手是"改名类工具"，不是隐写者
| 竞品 | 做了什么 |
|------|---------|
| rozx/Complex-unzip-tool-v2 | 文件名解伪装 |
| TR-Supowe | 同上 |
| **ccloli** | **2³² 偏移修补**（和我们同一个技术点！） |
| Butter-unpacker | 编码自适应 |

它们**已经做了**文件名解伪装 + GBK/Big5/UTF-16 编码自适应。
→ **我们的差异化打法**：它们只解决"文件名乱码"，**我们能真解隐写包**（多路提取 + 救援 + 分卷 + 中文密码）。
