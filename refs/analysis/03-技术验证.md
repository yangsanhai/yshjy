### 1.4 ⚠️ 性能陷阱：`Detect` 会读遍整个文件

```
文件 8711817691 字节 (8.7118 GB)
[自研定位]                   4.676ms   Δ_cd=119248031
[Detect + new]              113.058s
   （entry0 前 16 字节 377abcaf271c0004a405ae88401cda4a）
[Known(Δ_cd) + with_config]   69.264µs  ok=true
[Window(Δ_cd) + Detect]       95.060s  ok=true
```

| 路径 | 耗时 | 说明 |
|---|---|---|
| 自研定位 | **4.7 ms** | 只读尾部 512 KiB + CD 区 1 MiB |
| `Detect` + `new` | **113 s** | EOCD64 缓存从文件头扫到 locator 位置 ⇒ 读满 8.7 GB |
| `Known(Δ)` | **69 µs** | 直接在两处验证签名，最优解 |
| `Window` + `Detect` | **95 s** | 重标定后窗口仍是 8.6 GB，照样扫满 |

⇒ **正式版必须自研定位 + `ArchiveOffset::Known(Δ)`**。这比 zip2.md 的推测更严重：不只是「可能失败」，而是**必然慢 1600 倍**。自研解析我们已经在 spike 里用 Rust 实现了（`src/lib.rs::detect_zip_base`）。

### 1.5 情形 C 的补丁方案实测（这是本验证点最有价值的结论）

手工构造 ZIP64 小样本（`tools/make_zip64.py`）：垫 1000000 字节垃圾 + 把 locator 声明值改小 4096 ⇒ 制造出 `Δ_eocd = 1004096 ≠ Δ_cd = 1000000`：

```
── 方式 A：ZipArchive::new(File)
  ❌ [A naive] 失败: invalid Zip archive: Unexpected end of zip::format::blocks::ZipCentralEntryBlock
── 方式 B：with_config(Known(Δ_cd))
  ❌ [B Known(Δ_cd)] 失败: invalid Zip archive: Unexpected end of zip::format::blocks::ZipCentralEntryBlock
── 方式 C：Window 把 [Δ_cd, EOF) 重标定为 0 起点
  ❌ [C Window(Δ_cd)] 失败: invalid Zip archive: Unexpected end of zip::format::blocks::ZipCentralEntryBlock
── 方式 D：8 字节 locator 补丁（PatchWindow，base=0）
   把 @1004316 处 8 字节 locator 声明值 0x9c 改成 0x109c
  ✅ [D PatchWindow] 成功  entries=1
       archive_offset(Δ)=1000000 central_directory_start=1004167
       - [0] Ok("示例包.7z.001") comp=Stored size=4106 csize=4106 crc=1637d7b6
```

**结论（三重印证 zip2.md）**：
- `Known(n)` **不是**「告诉库 archive 从第几字节开始」的自由参数 —— ZIP64 下它被 locator 声明值钉死，救不了情形 C；
- `Window` 重标定也救不了（EOCD64/locator 的绝对语义被破坏）；
- **唯一解 = 补 locator 那 8 字节**；而且我们把它做成了**纯内存 PatchWindow，一个字节都不写盘**：

```rust
// src/lib.rs —— 只改读取路径上经过的字节，磁盘文件不动
pub struct PatchWindow { file: File, base: u64, len: u64, patches: Vec<(u64, Vec<u8>)> }
impl Read for PatchWindow {
    fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
        let start = self.file.stream_position()?;
        let n = self.file.read(&mut buf[..])?;          // 实际读取
        for (off, data) in &self.patches {              // 就地在返回缓冲区打补丁
            for (i, b) in data.iter().enumerate() {
                let a = *off + i as u64;
                if a >= start && a < start + n as u64 { buf[(a - start) as usize] = *b; }
            }
        }
        Ok(n)
    }
}
```

**关键**：Δ 不能再从 locator 推，必须**从真实 CDFH 扫描**得到（locator 已被篡改）。`detect_zip_base` 里就是这么做的：

```rust
// 从 CD 结束位置往前扫，找一段能「一路走通到 cd_end」的连续 CDFH 链
for &c in cands.iter().rev() {
    if let Some((_end, cnt)) = walk_cd(&w, win_from, c, cd_end) {
        if cnt >= 1 { first_cdfh_real = Some(c); cd_wellformed = true; break; }
    }
}
let delta_cd = first_cdfh_real.unwrap() as i128 - cd_offset_field as i128;
// 之后：new_declared = eocd64_real - delta_cd，写进 PatchWindow 的补丁表
```

- **完全流式**：解 64 MiB 只花 348 ms，峰值内存 **3.9 MB**（不是 8.6 GB）。`by_index(0)` 返回的 `ZipFile` 实现了 `Read`，按需解压。

### 1.8 验证点①结论

**能，有条件**：
1. 必做：自研 EOCD/EOCD64/locator/真实 CDFH 定位（spike 里已实现，~200 行）
2. 必做：用 `Config{archive_offset: ArchiveOffset::Known(Δ)}`，**不要用 `Detect`**（慢 1600 倍）
3. 备好：8 字节 locator 补丁的 `PatchWindow` 兜底（情形 C 唯一解）
4. 必开：`legacy-zip`
5. 限制：压缩条目不可随机访问；CD 扫描窗口暂设 1 MiB、尾部窗口 512 KiB（可调）

⇒ **`Window` 包装器完全解决问题**。而且 7z 内部偏移是**相对起点**的（start header 里存 `next_header_offset`），所以只需平移起点，**不需要像 ZIP64 那样打补丁**：

```rust
pub struct Window { file: File, base: u64, len: u64 }
impl Read for Window {
    fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
        let pos = self.file.stream_position()?;                 // 用绝对位置做窗口判断
        if pos < self.base { return Err(io::Error::new(ErrorKind::Other, "Window: 越界读取")); }
        let end = self.base + self.len;
        if pos >= end { return Ok(0); }
        let n = buf.len().min((end - pos) as usize);
        self.file.read(&mut buf[..n])
    }
}
impl Seek for Window {
    fn seek(&mut self, from: SeekFrom) -> io::Result<u64> {
        let abs: i128 = match from {
            SeekFrom::Start(p)   => self.base as i128 + p as i128,
            SeekFrom::End(p)     => (self.base as i128 + self.len as i128) + p as i128,
            SeekFrom::Current(p) => self.file.stream_position()? as i128 + p as i128,
        };
        let abs = abs as u64; self.file.seek(SeekFrom::Start(abs))?;
        Ok(abs - self.base)                                     // 对外返回窗口内偏移
    }
}
```

### 2.5 内存上限：**等于没有**，且无 API 可调 ⚠️

```rust
let sig = rars::find_archive_start(&head_bytes, head_bytes.len()).unwrap();  // offset 是绝对偏移
let a = match sig.family {
    rars::ArchiveFamily::Rar13     => rars::rar13::Archive::parse_path_with_signature_and_options(p, sig, opts).map(Archive::Rar13),

## 6. 踩坑记录（每条都实际踩过）

1. **`zip` 的 `Detect` 会读遍整个文件**：8.7 GB 文件 113 s（`Window` 里亦是 95 s）。**必传 `Known(Δ)`** → 69 µs。这是本次最值钱的一条。
2. **`zip2.md` 的结论直接适用于 `zip` 9.x**：`cargo info zip` 的 repository 是 `zip-rs/zip2`。别再去分辨 `zip` 和 `zip2` 两个包名。
3. **`Known(n)` 不是「起点参数」**：ZIP64 下 `archive_offset = 真实EOCD64位置 − locator声明值`，与 CD 真身无关；情形 C 下 `Known` 和 `Window` 都救不了，只有补 locator 那 8 字节。
4. **Δ 必须从「扫描到的真实 CDFH」推**，不能从 locator 推（locator 可能被篡改）。做法：从 CD 结束位置往前找一段能**连续走通到 `cd_end`** 的 CDFH 链。
5. **`zip::SUPPORTED_COMPRESSION_METHODS` 不可作能力判断**：开了 `legacy-zip` 也不列出 Implode/Shrink/Reduce，但实际能解。
6. **`by_index_seek` 对压缩条目直接报错**（`Seekable compressed files are not yet supported`），别指望随机访问。
7. **自研 `Concat` 的 `seek` 必须返回「全局逻辑位置」而不是「段内偏移」**：我第一版返回段内偏移，`Archive::read` 里 `seek(End(0))` 拿到 908321（真实 3005473）→ 报 `next header offset out of range`，排查了一轮。**这是最容易犯的 IO 包装器错误。**
8. **头加密 7z 连成员列表都拿不到**（`PasswordRequired`）；仅内容加密的能列名但不能取数据 —— 密码校验策略要按这个分两路。
9. **头加密的 RAR 分卷必须在「解析每个卷」时传密码**，否则 `a password is required`（不能只在 `extract_volumes_to` 阶段传）。
10. **RAR 错误密码的报错很不友好**：`input is too short`（`header_enc_1234.rar` 用错密码）—— 我们需要把这类底层错误映射成「密码错误」给用户。
11. **`rars::detect_archive_family` 只看 offset 0**，SFX 必须用 `find_archive_start`。
12. **`rars` 的 8 MiB SFX 扫描上限**：超过就只能自己扫 + family 级 API。
13. **`sevenz-rust2` 的 crates.io 包名就是 `sevenz-rust2`**（不必 git 依赖），写错成 `sevenz-rust` 会拉到停更的 dyz1990 0.6.1。
14. **`Password::from(&str)` 是 UTF-16LE**，与 7z CLI 约定一致；中文密码无需额外转码（12 字节 = 6 字符 × 2）。
15. **7z 造不出 Implode/Shrink zip**（`E_NOTIMPL : Not implemented`）——legacy 样本只能从 zip2 仓库测试数据取。
16. **7z CLI 无法打开我们的伪装包**（`Cannot open the file as [zip] archive`），但 `zip` crate 能 —— 所以「7-Zip 打不开」不能作为「文件坏了」的判据。
17. **工程约定**：本机禁止 heredoc / `python3 -c` / 写 `/tmp`（临时文件须落 `$TMPDIR`）。脚本一律 `write_file` 落盘再执行。

## 8. 对原方案的修正建议

1. **验证点① 的预判要改**：不是「`ZipArchive::new` 会失败」，而是**「会成功，但慢 1600 倍（113 s vs 69 µs）」**。方案里必须写死「自研定位 → `Known(Δ)`」，并把 `Detect` 路径视为**禁用**。
2. **brief 里的 2355200 应作废**，以本报告实测的 `Δ = 119248031`（三 Δ 相等，情形 A）为准。该文件**不需要** locator 补丁；补丁能力作为**情形 C 的兜底**保留（已验证可用）。
3. **7z 起点问题比报告描述的更简单**：`Window` 足够了，不需要补丁（7z 内部偏移是相对起点的）。真正要自己补的是**分卷 `Concat`** 和**内存护栏**。
4. **RAR 比预期好**：`rars` 自带 SFX 扫描（zip/7z 都没有），伪装包场景下 RAR 反而是三者里最省事的。
