## 先说结论（避免为凑数编造技术点）

**1. 「加一种格式只写一个 handler」不是设计出来的，是三件套语法糖的产物。**
`REGISTER_ARC_IO(...)` 一个宏调用同时干了三件事：① 生成静态 `CArcInfo` 元数据（签名/扩展名/标志位/工厂函数指针）；② 生成 `CreateArc`/`CreateArcOut` 两个工厂函数；③ 生成一个 `CRegisterArc` 全局对象，**靠 C++ 静态构造器在 `main()` 之前自动把元数据 push 进 `g_Arcs[]`**（`RegisterArc.h:44-71` + `ArchiveExports.cpp:18-28`）。
**Rust 没有静态构造器**，所以这条"零登记"红利拿不到。我们必须显式登记：`inventory` crate / `linkme::distributed_slice` / 或 `build.rs` 扫目录生成登记表。这是本清单里**最关键的一条落地决策**。

**2. 嗅探与 handler 是彻底解耦的，解耦靠「元数据下沉」。**
签名、签名偏移、扩展名、以及可选的 `IsArc(const Byte*, size_t) -> 0/1/2` 纯函数，**全部放在 handler 文件顶部的注册元数据里，不放在 handler 类里**。搜起点（含 SFX 前缀、非 0 偏移、多签名）由 `OpenArchive.cpp` 统一干，handler 收到的流**已经被 seek 到归档起点**。handler 自己从不搜索自己。

**3. 7-Zip 的 GUI 其实有"两个壳"，且它没有共享内核 API —— 它共享命令行。**
- `7zFM.exe`（FileManager，双栏文件管理器）：浏览归档**进程内**走 `IArchiveFolder`/`CAgent`（`UI/Agent/`）；但**压缩/解压不在进程内做**，而是拼命令行 `CreateProcess` 拉起 `7zG.exe`（`CompressCall.cpp:34,74-95`）。
- `7zG.exe`：纯进度对话框壳，用**和命令行完全同一个 `CArcCmdLineParser`** 解析参数（`GUI.cpp:153-157` vs `Console/Main.cpp:908` 同款），内核在 `UI/Common` 里。

→ 对我们：我们是 Rust 库 + 双壳，**本来就比它更干净**（进程内调用而非 spawn 子进程）。真正值得抄的是"**同一套参数模型同时喂 CLI 和 GUI**"和"**回调 trait 由壳实现、内核只吐数据**"。**不要抄它 spawn 子进程**（违反我们一体化原则）。

**4. 取消机制只有一条路：回调函数返回 `E_ABORT`（`0x80004004`）。**
没有独立的取消通道、没有 `AtomicBool` 放进内核。控制台壳是 SIGINT 计数器（连按 3 次才硬退，`ConsoleClose.cpp:18-19`）；GUI 壳是 `CProgressSync._stopped` 标志位（`ProgressDialog2.cpp:571`）。内核在每个 `SetCompleted`/`SetRatioInfo` 里检查返回码。
→ 我方 `src/io/interrupt.rs` 的 `Arc<AtomicBool>` + 每 1 MiB 检查，**粒度比它更细、更可靠**，这条我们已领先，不做回退。

**5. 本地化是「单个 UTF-8 文本文件 + 隐式 id 序列 + 二分查找 + 编译期资源串兜底」。**
翻译文件不在本仓库（7-Zip 的 `Lang/*.txt` 是独立下载包），所以**"怎么组织一份翻译、怎么分发给翻译者"这一层我只能从加载器反推，标 ❓**；但**加载/查找/回退机制**是完整可读的（`Common/Lang.cpp`）。
